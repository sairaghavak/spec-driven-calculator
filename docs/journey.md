# Journey log

How this repo was built, one step at a time, with GitHub Spec Kit and Claude Code. Each step has a git tag: run `git checkout step-NN-<slug>` to see the repo exactly as it was after that step.

## Pre-work (no repo changes)
- Refined the author's private, user-level `~/.claude/CLAUDE.md`: removed duplicate rules, added Go defaults, a public-repo guard, and a "review before commit" rule (show the changes and stop; ask to commit only after the author is satisfied). It is not part of this repo, which is the point: any rule this repo's spec-driven workflow depends on must live in the repo, or a fresh clone gets a different assistant.
- Chose the spec format. Options: plain Markdown requirements, Given/When/Then scenarios, or a tool-driven workflow. Picked GitHub Spec Kit because it is open source, agent-agnostic, and widely recognized. Trade-off accepted: it is labeled experimental, so the version is pinned.

## Step 00 · Project rules · tag: step-00-project-rules
- Goal: write the project rules in `CLAUDE.md` (how Claude Code works in this repo) and start this journey log, before any Spec Kit or calculator work.
- Command/prompt: "I wanted you to have a log of all the sequence of steps and finally draft an excalidraw diagram to understand the state of the project from init to featureX. And also the commit history should tell the story and must be demoable when I am trying to explain the spec-driven development as a tech talk"
- AI produced: `CLAUDE.md` (workflow, journey-log format, commit/tag conventions, Go rules), `docs/journey.md`
- Human review, in rounds:
  1. Removed a "public-repo hygiene" section: it protected the author's privacy but did not change how this repo gets built. Test: would a fresh clone behave wrongly without this line?
  2. Questioned "(non-negotiable)" and "no code without an approved spec". Emphasis words do not enforce anything (CLAUDE.md is a prompt, not a guardrail), and "approved" was undefined. Now: approval = reviewed, then committed and tagged; Go code only for a task in a committed `tasks.md`.
  3. Asked whether the phase order matched Spec Kit. Verified by running `specify init` 1.4.0 in a scratch folder outside this repo: the draft rules were missing `checklist`, `analyze`, and `converge`, used a nonexistent `--ai` flag, and assumed feature branches are created by default (they need `--extension git`).
  4. Kept `checklist` so no phase is skipped; corrected the step count to 8 phases and 9 commits per feature (implement = red + green).
  5. Added missing commit types (`docs:`, `docs(tasks):`) and made `--no-ff` merge commits untagged on purpose.
  6. Asked whether this journey log is needed at all, since git can hold the same text. Kept it: prompts, human review, and pre-work have no other home, and most readers never clone. Removed the duplication instead: commit message = subject plus one line of why, tag = one-line summary, journey = detail.
  7. Renamed this step from "Demo rules" (unclear: demo of what?) to "Project rules". Kept zero-padded numbers (`step-00`) because git sorts tags as text: unpadded, `step-10` lists before `step-2`.
  8. Asked what the "Spec Kit section markers" rule meant. It came from older Spec Kit versions, where `plan` ran `update-agent-context.sh` to rewrite a marked block in `CLAUDE.md`. Checked 1.4.0: that script is no longer shipped and nothing touches `CLAUDE.md`. Deleted the rule; if Spec Kit starts editing the file, the diff review will show it and the rule comes back based on observed behavior.
  9. Removed ambiguous wording, prompted by "does this mean X or Y?" questions: "demo" could mean the repo, the calculator, or the talk; "the spec" was being read as `CLAUDE.md`. Fixed by naming the thing: "spec" now only ever means `specs/NNN-*/spec.md`, rules point to exact files, ID examples (`FR-001`, `T012`) were checked against Spec Kit's templates, and every entry gained a Goal line and a precise definition of Command/prompt and Lesson.
- Lesson: Don't trust AI-written project rules (here, `CLAUDE.md`) until you've checked them against the tool they describe (here, Spec Kit), and treat every "what does this mean?" question from a reviewer as a wording bug to fix.

## Step 01 · Spec Kit init · tag: step-01-speckit-init
- Goal: install Spec Kit 1.4.0 into this repo with the Claude Code integration, so the later phases can run as `/speckit-*` commands.
- Command/prompt: `specify init --here --force --non-interactive --integration claude`
- AI produced: 29 new files; `specify init` changed no existing file (`CLAUDE.md` untouched by init, confirming Step 00 round 8).
  - `.claude/skills/speckit-*/SKILL.md` (9): one skill per phase: constitution, specify, clarify, plan, checklist, tasks, analyze, implement, converge.
  - `.specify/` (20): templates, helper scripts, the workflow definition, and a placeholder `memory/constitution.md`, filled in at Step 02.
  - `.gitignore`: added `.claude/settings.local.json` after init warned that agent folders can hold credentials. `.claude/skills/` stays committed because a fresh clone needs it.
- Human review, in rounds:
  1. First attempt also passed `--extension git` (as the Step 00 rules required) and produced 57 files, including auto-commit hooks around every phase (all disabled by default). The author rolled it back: too much for a newcomer to wade through, and the only benefit was branch creation, which `git checkout -b 001-<name>` already does. Updated `CLAUDE.md` to drop the extension and create feature branches by hand, then re-ran init.
  2. Considered skipping the tool and following Spec Kit's method by hand (zero files up front). Kept the tool: the talk should show a real, recognized toolkit the audience can install and replay.
  3. Asked whether each change should reach `main` through a PR. Yes, one PR per branch, not per step: the per-step review already happens before each commit, and the PR reviews the whole unit. Moved the unpushed Step 00 commit from `main` to a new `000-project-setup` branch, which will carry Steps 00 to 02. PRs must use "Create a merge commit", because squash or rebase would leave the step tags off `main`.
  4. Asked twice who a "Lesson" is for. Renamed the field to "Takeaway for readers" from this step on, since the label itself was the ambiguity. Step 00 above still keeps "Lesson" because the log is append-only.
- Takeaway for readers: Install only the parts of a tool you need, and keep the repo readable for newcomers. Here, Spec Kit's optional git extension (`--extension git`) added 28 files and auto-commit hooks, yet its only benefit was creating each feature branch automatically, which one command (`git checkout -b 001-basic-arithmetic`) does by hand.

## Step 02 · Constitution · tag: step-02-constitution
- Goal: fill Spec Kit's constitution with the calculator's engineering principles, so that every later phase can check its output against them.
- Command/prompt: `/speckit-constitution Four principles: (1) Spec-first traceability: every behavior traces to a requirement ID (FR-xxx) in a committed spec.md; unspecified behavior is a defect. (2) Test-first: tests are written from the spec and fail before implementation (red commit, then green commit); each test cites the requirement it verifies. (3) Simplicity: Go standard library only unless a spec justifies a dependency; no abstraction without a current requirement. (4) Explicit errors: invalid input and edge cases return Go error values with defined behavior; no panics for expected failures. Additional constraints: Go 1.27, module github.com/sairaghavak/spec-driven-calculator; gofmt, go vet, and go test ./... must pass before any green commit. Development workflow: Spec Kit phases in order with author review gates; the commit is the approval. Governance: amendments via pull request, semantic versioning, compliance checked in /speckit-analyze. Ratified 2026-11-18. Keep a top-of-file HTML comment explaining what this file means for Claude.`
- AI produced: `.specify/memory/constitution.md` v1.0.0. All template placeholders were replaced, and the template's fifth principle slot was dropped because only four principles were requested. The skill also adds a temporary "Sync Impact Report" comment at the top; it was removed before committing, as the skill instructs.
- Human review, in rounds:
  1. Asked what the constitution is. It holds product principles, not Spec Kit settings. `CLAUDE.md` says how Claude works in this repo; the constitution says what every version of the calculator must satisfy. All 9 phase skills read it, but at this point Claude Code did not load it automatically (round 5 changes that).
  2. Asked for a comment at the top of both `CLAUDE.md` and the constitution, explaining what each file means for Claude. Added both. The command above also asks for the constitution's comment, so that future amendments keep it.
  3. Moved the Go section of `CLAUDE.md` (stdlib only, the quality gate, tests citing `FR-` IDs) into the constitution and replaced it with a single line pointing there, so that no rule is written twice.
  4. Left the product's shape (CLI, library, or both) out on purpose: that is a decision for the first feature's spec, not a principle.
  5. A pointer line only tells Claude where the principles are; Claude does not see their content unless it reads the file. Added the import line `@.specify/memory/constitution.md` to `CLAUDE.md`, which loads the constitution into Claude's context in every session. Cost: about 750 tokens per request, mostly served from the prompt cache. Benefit: the principles apply to all work and survive context compaction. Updated the constitution's top comment to match.
  6. Reworded the amendment rule to "Amendments in this file **MUST** be made with `/speckit-constitution`", and made every MUST and MUST NOT bold so readers can spot the hard requirements at a glance.
- Takeaway for readers: Put the principles every feature must meet in the constitution and the agent's working rules in `CLAUDE.md`, and write principles as testable statements (here, "returns an `error`, never panics"), because an LLM interprets them, not a compiler.

## Step 03 · Specify · tag: step-03-specify
- Goal: turn the author's one-paragraph feature idea into a testable spec for feature 001, with requirement IDs that tests and code will cite.
- Command/prompt: `/speckit-specify Add feature to do basic math operations like addition, subtraction, multiplication, divison in the CLI and prompt the user whenever there is bad input or errors while computing the math operations, keep things default for now and for multiplication accept the numbers only upto 200 like 199 * 199 is valid 200 * 200 is bad input that should respond with proper user informative message`
- AI produced: `specs/001-basic-arithmetic/spec.md` (4 user stories, 13 functional requirements FR-001 to FR-013, 4 success criteria) and `specs/001-basic-arithmetic/checklists/requirements.md` (the skill's spec quality checklist, all 16 items passing). The branch `001-basic-arithmetic` was created by hand beforehand; the skill named the spec folder to match.
- Human review, in rounds:
  1. The prompt said "up to 200" but its example rejects 200. The AI followed the example (each operand must be below 200) and recorded the choice under Assumptions, instead of guessing silently.
  2. The skill raised 2 `[NEEDS CLARIFICATION]` questions. Interaction mode: answered "both" (one-shot when an operation is given at start, interactive session otherwise), which added User Story 4 and FR-011 to FR-013. Negative operands under the multiplication limit: answered "limit on size", so operands must be strictly between -200 and 200 (FR-008).
  3. Asked whether each user story should cover a set of FRs. Answer: many-to-many, but every FR needs at least one story's acceptance scenario, or `/speckit-tasks` (which groups tasks by story) can drop it. Mapping the stories to FRs showed FR-009 (result too large) only under Edge Cases, so it got an acceptance scenario in Story 2.
  4. Tried `/speckit-analyze` at this point; it aborted because `plan.md` and `tasks.md` do not exist yet. It checks spec, plan, and tasks against each other, so it only works after `/speckit-tasks`.
- Takeaway for readers: Give the agent a concrete example next to every rule ("199 * 199 is valid, 200 * 200 is not"). Here the example settled what "up to 200" meant, and the spec now records the boundary on both sides of 200, which becomes the test cases.

## Step 04 · Spec template · tag: step-04-spec-template
- Goal: change Spec Kit's spec layout to requirements first, then user stories, in agile terms, for this and every future feature.
- Command/prompt: "I'd like understand why the spec.md is so long and I don't like the order of the content in the spec file. I think first the Functional Requirements section should be present and then NFR's if applicable and then the User stories And, I don't understand the Success Criteria Section. Is this section mandatory according to spec-kit framework? If not could we simplify and make it more relatable to the regular agile delivery model I mean use commonly used terminology"
- AI produced:
  - `.specify/templates/overrides/spec-template.md` (new): Summary, Scope (an `[!IMPORTANT]` callout with In scope and Out of scope), Functional Requirements, Non-Functional Requirements, User Stories ("As a ... I want ... so that ...", Covers, Acceptance Criteria), Edge Cases, Key Entities, Assumptions, Definition of Done. Spec Kit's template resolver checks `overrides/` first, so `/speckit-specify` uses it from now on; the pinned core template is untouched.
  - `specs/001-basic-arithmetic/spec.md` restructured to the new layout with the same meaning: SC-004 became NFR-001, SC-003 became NFR-002, SC-001 and SC-002 became the Definition of Done; "Why this priority" and "Independent Test" paragraphs dropped (the acceptance criteria are the independent test); edge cases already shown in a story removed, the rest cite their FR. 199 to 179 lines, 1760 to 1566 words (11% shorter, after round 6).
  - `CLAUDE.md`: rule that the NFR section plays the role of Spec Kit's Success Criteria for the `speckit-*` skills, and that template changes are process steps with their own commit and tag; the per-feature count is now "9 phase commits plus one per process step".
  - `checklists/requirements.md`: Success Criteria items renamed to NFRs.
- Human review, in rounds:
  1. Asked whether Success Criteria is mandatory. The template labels it so, but no code enforces it; three skills (clarify, analyze, converge) refer to it by name, hence the mapping rule in `CLAUDE.md` instead of silently renaming. Spec Kit's own checklist skill already uses `NFR-#`.
  2. Section order does not matter to the skills: they are instructions an LLM interprets and find sections by name, not position.
  3. Chose a project override over editing only spec 001, so feature 002 starts in the same layout, and a separate step over folding the change into clarify, so each commit holds one kind of change.
  4. The restructure surfaced two inconsistencies, fixed without changing meaning: the old Story 3 still said "below 200" after FR-008 became "strictly between -200 and 200", and "extra spaces are ignored" was an edge case with no FR behind it (a Principle I gap), now part of FR-001.
  5. The AI estimated the new layout would cut about 40%; the result was 15% before round 6 added the Scope section, because the 13 FRs and the concrete examples (the future test cases) were kept as they were. The length that remains is mostly requirements, not template prose.
  6. The author pointed out that the spec never said up front that a calculation takes exactly two operands; "one operation at a time" sat in FR-001 and "chained expressions" in Out of Scope at the bottom. Added a Scope section right under the Summary, as a GitHub `[!IMPORTANT]` callout naming `2 * 10 + 15 - 50` as unsupported, to the template and to spec 001; moved Out of Scope there so it is written once; turned that example into US2 acceptance criterion 6 (replacing the `2 + 3 + 4` edge case). The Input quote stays as typed, because it records the author's original prompt verbatim; at the author's request, a `[!NOTE]` right after it (spec 001 only, not the template) says the prompt set no operand count and the spec limits it to two.
- Takeaway for readers: Adapt the framework's templates to the vocabulary your team already uses, through its override mechanism rather than by editing its core files, and write down how your names map to the framework's names so its commands keep working.

## Step 05 · Clarify · tag: step-05-clarify
- Goal: resolve the spec's remaining decisions that would change tests, before planning starts.
- Command/prompt: `/speckit-clarify`
- AI produced: `specs/001-basic-arithmetic/spec.md` with a `## Clarifications` section (session 2026-11-21, 5 questions, the skill's maximum) and the answers applied to the requirements: FR-001 (spaces optional, rule for a `-` sign), FR-004 (round to 5 decimal places), FR-009 retired, FR-012 (exact welcome message), new FR-014 (at most 3 digits before and 2 after the decimal point) and FR-015 (`Errors:` headline with one list item per problem), plus matching acceptance criteria and edge cases. Spec quality checklist: 16/16 before and after.
- Human review, in rounds:
  1. Display of inexact results: the AI recommended 15 significant digits; the author chose 5 decimal places (`1 / 3` shows `0.33333`).
  2. Spaces: optional (`2+3`, `-3-2`, `5*-2` all valid), as recommended.
  3. Input size: the AI recommended rejecting numbers too large to hold; the author chose a 3-digit limit instead, then (asked whether it counts decimals) 3 digits before the point, and later added 2 digits after it. Since no result can now overflow, FR-009 was retired as "Removed" rather than deleted or reused, because Step 03's committed history refers to it.
  4. Input breaking several rules: the AI recommended reporting only the first; the author chose all of them, under an explicit `Errors:` headline, one list item per line.
  5. Interactive prompt: instead of the suggested `calc> `, the author gave an exact welcome message shown once, with each result or `Errors:` block on a new line.
  6. Review: the author corrected the welcome text to end "Please enter your input" and asked for `Please enter your input.` on a new line after every result or `Errors:` block (FR-012, US4). Then the welcome became four lines: the two sentences on their own lines, a line of 45 `=`, and `Please enter your input. Example: 10/5`. The period after the `/` at the end of the second line was dropped, so users do not read it as part of the operator list. Finally, on the AI's recommendation and the author's follow-ups: the welcome became six lines (a rewritten second line, "A spec-driven development demo, built with GitHub Spec Kit."; an operator line; the author's idea of stating the 2-number rule up front), each answer is labelled `Result: <value>` to pair with `Errors:`, a line of `-` separates exchanges (both separators widened from 45 to 59 characters to match the welcome's longest line), and one-shot mode keeps printing the bare value so scripts can capture it (FR-011).
- Takeaway for readers: Treat the agent's recommended option as a starting point, not the answer. Here the author overrode 3 of 5 recommendations, and each override (a digit limit, all errors at once, a welcome text) is a product decision only the owner can make; the clarify step's value is that it forces those decisions before any test is written.

## Step 06 · Spec amendment · tag: step-06-leading-zeros
- Goal: close a spec gap found after clarify: numbers with leading zeros had no defined behavior.
- Command/prompt: "Technically there is no meaning for leading zeros right like 007 or 00.5 0999 so Reject them as malformed numbers with proper Error reason"
- AI produced: `specs/001-basic-arithmetic/spec.md`: a sixth Clarifications entry, marked as added by the author after the clarify session; FR-003 rejects a whole-number part that starts with `0` unless it is exactly `0` (`007`, `00.5`, `0999` malformed; `0.5`, `0` valid); FR-006 requires a leading-zeros message instead of the generic "not a number"; edge cases `007 + 1`, `00.5 * 2`, `0999 - 1`, `-007 + 1` rejected and `0.5 * 2`, `0 + 1` valid; an Assumptions line leaving the output stream and one-shot exit-status values (FR-011) to the plan.
- Human review, in rounds:
  1. Before planning, the AI listed three open items. It first called all three plan decisions, then corrected itself: leading zeros are user-visible behavior, so under Principle I they belong in the spec. FR-003 accepted `007`, and FR-014 did not say whether leading zeros count toward the 3-digit limit, so two implementations could disagree.
  2. The AI offered two rules (accept and ignore leading zeros, or reject them); the author chose reject, with a specific error reason. In FR-015's error order the check sits in the "not a number" slot, so `007 * 300` reports the leading zeros, then the multiplication limit.
  3. The other two items (error output stream and exit codes; shell expansion of `*`) were left to `/speckit-plan`. The `*` item was already in Assumptions; the stream and exit-code item existed only in Claude's memory, so a line was added to Assumptions (see Step 07).
  4. The AI planned to fold this into the plan commit; the author asked for its own step, so the plan commit holds only plan output.
- Takeaway for readers: A gap found after clarify still goes into the spec, not into the code or someone's memory. Before planning, the fix costs one edit and one commit; once tests exist, the same decision costs a red-green cycle.
