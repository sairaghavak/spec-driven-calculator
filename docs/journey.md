# Journey log

How this repo was built, one step at a time, with GitHub Spec Kit and Claude Code. Each step has a git tag: run `git checkout step-NN-<slug>` to see the repo exactly as it was after that step.

In this log, "the author" is the repo owner, [sairaghavak](https://github.com/sairaghavak), who reviews and approves every step. "The AI" is Claude Code, which ran the Spec Kit commands and drafted the files.

## Pre-work (no repo changes)
- Refined the author's private, user-level `~/.claude/CLAUDE.md`: removed duplicate rules, added Go defaults, a public-repo guard, and a "review before commit" rule (show the changes and stop; ask to commit only after the author is satisfied). It is not part of this repo, which is the point: any rule this repo's spec-driven workflow depends on must live in the repo, or a fresh clone gets a different assistant.
- Chose the spec format. Options: plain Markdown requirements, Given/When/Then scenarios, or a tool-driven workflow. Picked GitHub Spec Kit because it is open source, agent-agnostic, and widely recognized. Trade-off accepted: it is labeled experimental, so the version is pinned.

  3. Asked whether the phase order matched Spec Kit. Verified by running `specify init` 1.4.0 in a scratch folder outside this repo: the draft rules were missing `checklist`, `analyze`, and `converge`, used a nonexistent `--ai` flag, and assumed feature branches are created by default (they need `--extension git`).

  7. Renamed this step from "Demo rules" (unclear: demo of what?) to "Project rules". Kept zero-padded numbers (`step-00`) because git sorts tags as text: unpadded, `step-10` lists before `step-2`.

  9. Removed ambiguous wording, prompted by "does this mean X or Y?" questions: "demo" could mean the repo, the calculator, or the talk; "the spec" was being read as `CLAUDE.md`. - Lesson: Don't trust AI-written project rules (here, `CLAUDE.md`) until you've checked them against the tool they describe (here, Spec Kit), and treat every "what does this mean?" question from a reviewer as a wording bug to fix.

## Step 02 · Constitution · tag: step-02-constitution
- Goal: fill Spec Kit's constitution with the calculator's engineering principles, so that every later phase can check its output against them.
- Command/prompt: `/speckit-constitution Four principles: (1) Spec-first traceability: every behavior traces to a requirement ID (FR-xxx) in a committed spec.md; unspecified behavior is a defect. (2) Test-first: tests are written from the spec and fail before implementation (red commit, then green commit); each test cites the requirement it verifies. (3) Simplicity: Go standard library only unless a spec justifies a dependency; no abstraction without a current requirement. (4) Explicit errors: invalid input and edge cases return Go error values with defined behavior; no panics for expected failures. Additional constraints: Go 1.27, module github.com/sairaghavak/spec-driven-calculator; gofmt, go vet, and go test ./... must pass before any green commit. Development workflow: Spec Kit phases in order with author review gates; the commit is the approval. Governance: amendments via pull request, semantic versioning, compliance checked in /speckit-analyze. Ratified 2026-11-18. Keep a top-of-file HTML comment explaining what this file means for Claude.`
- AI produced: `.specify/memory/constitution.md` v1.0.0. All template placeholders were replaced, and the template's fifth principle slot was dropped because only four principles were requested. The skill also adds a temporary "Sync Impact Report" comment at the top; it was removed before committing, as the skill instructs.
- Human review, in rounds:
  1. Asked what the constitution is. It holds product principles, not Spec Kit settings. `CLAUDE.md` says how Claude works in this repo; the constitution says what every version of the calculator must satisfy. All 9 phase skills read it, but at this point Claude Code did not load it automatically (round 5 changes that).
  2. Asked for a comment at the top of both `CLAUDE.md` and the constitution, explaining what each file means for Claude. Added both. The command above also asks for the constitution's comment, so that future amendments keep it.
  3. Moved the Go section of `CLAUDE.md` (stdlib only, the quality gate, tests citing `FR-` IDs) into the constitution and replaced it with a single line pointing there, so that no rule is written twice.
  4. Left the product's shape (CLI, library, or both) out on purpose: that is a decision for the first feature's spec, not a principle.
  5. A pointer line only tells Claude where the principles are; Claude does not see their content unless it reads the file. Added the import line `@.specify/memory/constitution.md` to `CLAUDE.md`, which loads the constitution into Claude's context in every session. Cost: about 750 tokens per request, mostly served from the prompt cache. Benefit: the principles apply to all work and survive context compaction. Updated the constitution's top comment to match.
  6. Reworded the amendment rule to "Amendments in this file **MUST** be made with `/speckit-constitution`", and made every MUST and MUST NOT bold so readers can spot the hard requirements at a glance.
- Takeaway for readers: Put the principles every feature must meet in the constitution and the agent's working rules in `CLAUDE.md`, and write principles as testable statements (here, "returns an `error`, never panics"), because an LLM interprets them, not a compiler.

## Step 03 · Specify · tag: step-03-specify
- Goal: turn the author's one-paragraph feature idea into a testable spec for feature 001, with requirement IDs that tests and code will cite.
- Command/prompt: `/speckit-specify Add feature to do basic math operations like addition, subtraction, multiplication, divison in the CLI and prompt the user whenever there is bad input or errors while computing the math operations, keep things default for now and for multiplication accept the numbers only upto 200 like 199 * 199 is valid 200 * 200 is bad input that should respond with proper user informative message`
- AI produced: `specs/001-basic-arithmetic/spec.md` (4 user stories, 13 functional requirements FR-001 to FR-013, 4 success criteria) and `specs/001-basic-arithmetic/checklists/requirements.md` (the skill's spec quality checklist, all 16 items passing). The branch `001-basic-arithmetic` was created by hand beforehand; the skill named the spec folder to match.
- Human review, in rounds:
  1. The prompt said "up to 200" but its example rejects 200. The AI followed the example (each operand must be below 200) and recorded the choice under Assumptions, instead of guessing silently.
  2. The skill raised 2 `[NEEDS CLARIFICATION]` questions. Interaction mode: answered "both" (one-shot when an operation is given at start, interactive session otherwise), which added User Story 4 and FR-011 to FR-013. Negative operands under the multiplication limit: answered "limit on size", so operands must be strictly between -200 and 200 (FR-008).
  3. Asked whether each user story should cover a set of FRs. Answer: many-to-many, but every FR needs at least one story's acceptance scenario, or `/speckit-tasks` (which groups tasks by story) can drop it. Mapping the stories to FRs showed FR-009 (result too large) only under Edge Cases, so it got an acceptance scenario in Story 2.
  4. Tried `/speckit-analyze` at this point; it aborted because `plan.md` and `tasks.md` do not exist yet. It checks spec, plan, and tasks against each other, so it only works after `/speckit-tasks`.
- Takeaway for readers: Give the agent a concrete example next to every rule ("199 * 199 is valid, 200 * 200 is not"). Here the example settled what "up to 200" meant, and the spec now records the boundary on both sides of 200, which becomes the test cases.

## Step 06 · Spec amendment · tag: step-06-leading-zeros
- Goal: close a spec gap found after clarify: numbers with leading zeros had no defined behavior.
- Command/prompt: "Technically there is no meaning for leading zeros right like 007 or 00.5 0999 so Reject them as malformed numbers with proper Error reason"
- AI produced: `specs/001-basic-arithmetic/spec.md`: a sixth Clarifications entry, marked as added by the author after the clarify session; FR-003 rejects a whole-number part that starts with `0` unless it is exactly `0` (`007`, `00.5`, `0999` malformed; `0.5`, `0` valid); FR-006 requires a leading-zeros message instead of the generic "not a number"; edge cases `007 + 1`, `00.5 * 2`, `0999 - 1`, `-007 + 1` rejected and `0.5 * 2`, `0 + 1` valid; an Assumptions line leaving the output stream and one-shot exit-status values (FR-011) to the plan.
- Human review, in rounds:
  1. Before planning, the AI listed three open items. It first called all three plan decisions, then corrected itself: leading zeros are user-visible behavior, so under Principle I they belong in the spec. FR-003 accepted `007`, and FR-014 did not say whether leading zeros count toward the 3-digit limit, so two implementations could disagree.
  2. The AI offered two rules (accept and ignore leading zeros, or reject them); the author chose reject, with a specific error reason. In FR-015's error order the check sits in the "not a number" slot, so `007 * 300` reports the leading zeros, then the multiplication limit.
  3. The other two items (error output stream and exit codes; shell expansion of `*`) were left to `/speckit-plan`. The `*` item was already in Assumptions; the stream and exit-code item existed only in Claude's memory, so a line was added to Assumptions (see Step 07).
  4. The AI planned to fold this into the plan commit; the author asked for its own step, so the plan commit holds only plan output.
- Takeaway for readers: A gap found after clarify still goes into the spec, not into the code or someone's memory. Before planning, the fix costs one edit and one commit; once tests exist, the same decision costs a red-green cycle.
